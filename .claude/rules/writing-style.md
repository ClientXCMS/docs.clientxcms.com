# Style de rédaction

- Aucun deux-points en plein milieu de phrase pour enchaîner deux propositions (`Résultat : l'item s'insère...`, `Le champ X : fait Y`). Le deux-points est réservé à l'introduction d'une liste, d'une citation ou d'un exemple de code - jamais à relier deux idées qui devraient être deux phrases ou une seule phrase coordonnée. Reformuler avec une conjonction de coordination (et, mais, ou, donc, car, ni, or) ou couper en deux phrases.
  - Mauvais : `Résultat : l'item s'insère dans le menu à la position donnée.`
  - Bon : `L'item s'insère alors dans le menu à la position donnée.`
  - Mauvais : `Le champ Description utilise un éditeur Markdown : il propose gras, italique, titres.`
  - Bon : `Le champ Description utilise un éditeur Markdown qui propose gras, italique et titres.`
- Aucun emoji, nulle part dans la doc.
- L'analogie est l'exception, jamais un réflexe d'écriture ni une décoration. Par défaut on explique directement, sans détour.
- Une analogie ne se pose que si, sans elle, un concept technique reste réellement difficile à saisir - jamais pour illustrer quelque chose déjà clair.
- Rester sobre sur l'ensemble d'une page, pas seulement éviter de répéter le même type d'image : plusieurs analogies qui s'enchaînent, même différentes, cassent la clarté au lieu de la servir.
- Quand une analogie est posée, elle doit parler à un public large (vie quotidienne, comparaison universelle), jamais à une niche technique différente du sujet traité.
